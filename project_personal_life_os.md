Schema — 3 new tables, all under `finance` group in `config_resources.php`/nav:
- `salary_profiles`: company_name, position, basic_salary, salary_frequency (monthly/biweekly/weekly/custom), salary_payment_day, bank_account_id (fk), employee/employer_epf_percent (defaults), start_date, end_date, status (active/inactive), notes. Pure template — editing or deactivating one never touches historical `salary_payments`.
- `salary_payments`: salary_profile_id (fk, **nullable** — a payment can exist with no profile at all, for pure freelance/one-off income, matching the doc's "no salary month" / non-fixed-income requirement), payment_date, period_label, basic_salary/allowance/bonus/commission/other_addition (separate columns per doc §10, not a dynamic child-table — judged the generic flat-field CRUD engine couldn't reasonably support a repeating-component sub-form, and explicit columns for the 5 common components is a reasonable compromise), employee/employer_epf_percent+amount (both stored as **snapshots at payment time**, satisfying doc §7's immutability requirement — changing a profile's default % later never touches these), other_deductions, net_salary (required — the real deposited amount), bank_account_id (required), **transaction_id** (fk → transactions, auto-managed, see sync logic below).
- `epf_contributions`: salary_payment_id (fk, nullable — nullable specifically to allow manually-logged additional/voluntary contributions not tied to any payment), contribution_date, employee/employer/additional_contribution, notes. `ON DELETE CASCADE` from salary_payments.

**The important part — automatic write-time sync** (`sync_salary_payment()` in `api.php`, called from the `create`/`update` branches for resource `salary_payments`, satisfying the doc's explicit "must be linked to actual bank transactions and EPF records without duplicating financial amounts"):
- On create: inserts one `transactions` row (type=income, category=薪水, bank_account_id, amount=net_salary, description="{period_label} 薪资", date=payment_date), writes the new transaction's id back into `salary_payments.transaction_id`; if `employee_epf_amount + employer_epf_amount > 0`, also inserts one `epf_contributions` row.
- On update: if `transaction_id` already set, UPDATEs that same transaction's category/account/amount/date/description in place (does not create a second one); UPDATEs the existing `epf_contributions` row keyed by `salary_payment_id` if one exists, creates one if the EPF total just became >0, deletes it if the EPF total just became 0.
- On delete (special-cased in the `delete` action, `resource === 'salary_payments'`): explicitly deletes the linked `transactions` row via the stored `transaction_id` (no DB-level cascade exists in that direction — `transactions` doesn't reference `salary_payments`) before deleting the payment row itself; `epf_contributions` cleans up on its own via the `ON DELETE CASCADE` FK.
- All three directions (create/update/delete) verified end-to-end via direct API calls: RM5000 basic → RM550/RM650 EPF → RM4450 net produced a matching income transaction + EPF row; editing net_salary to 4600 correctly propagated to the linked transaction; deleting the payment correctly removed both the transaction and the EPF row (counts went 1→0 for both).

**Dashboard additions** (`build_dashboard()` in `api.php` + new cards in `renderDashboard()` in `app.js`): `expected_monthly_salary` (sum of `basic_salary` across `status='active' AND salary_frequency='monthly'` profiles — an approximation, doesn't attempt to prorate biweekly/weekly profiles into a monthly figure) vs `actual_monthly_salary` (sum of this calendar month's `salary_payments.net_salary`) shown side by side in a "💼 本月薪资" card — this is doc §12's Expected-vs-Actual principle, made concrete: **expected is never counted as actual income anywhere**, it's purely a separate display figure. `epf_cumulative` (all-time sum of employee/employer/additional across `epf_contributions`) shown in a "🏦 EPF 累计供款" card.

**Form UX** (`setupSalaryPaymentAutofill()` in `app.js`, wired into `openForm()` specifically for `resource === 'salary_payments'`, new-record only — never runs when editing an existing payment, so historical records can't get silently recalculated just by opening them, which is exactly the immutability behavior the doc insists on): picking a `salary_profile_id` in the dropdown pulls that profile's `basic_salary`/`employee_epf_percent`/`employer_epf_percent`/`bank_account_id` into the form; any change to basic/allowance/bonus/commission/other_addition/either EPF % recomputes suggested `employee_epf_amount`/`employer_epf_amount` (EPF calculated on `basic_salary` only, not allowances/bonus/commission — a reasonable simplification of Malaysian EPF's actual "wages" definition, not a legal citation) and `net_salary` — but every one of these computed fields remains a normal editable input, so the user can override any number by hand afterward, satisfying doc §7's explicit override requirement. **v3.4 (2026-09-22, later same day): the recurring "为什么我没看到更新" bug, finally root-caused and fixed for good.** This exact complaint has now happened multiple times across sessions (see the v2-era note above about "都没改变啊" turning out to be a scope misunderstanding, not this). This should be the permanent fix; the asset `?v=` bumping is still needed on top of it (for the JS/CSS themselves) but no longer depends on the user doing a hard-refresh — a normal refresh (or even just reopening the tab) should now always see the latest version. **If this complaint ever recurs after this fix, don't repeat the whole cache-diagnosis dance — suspect something else first** (this class of bug should now be closed).

Fix — the period-end choice depends on *why* the period is partial, not just whether it is:
- New hire, still employed (`start_date` after this month's 1st, no `end_date` this month): period = `start_date → payment_date`.
- Departing employee (`end_date` within this month): period = `month_start (or start_date) → end_date` — bounded by the real departure date regardless of payday timing.
- Neither: no prorating, full `basic_salary` — this must hold regardless of which day the payday falls on, so `$isFullMonth` is now its own direct boolean (`!$hasPartialStart && !$hasPartialEnd`), decoupled from whatever period-end value gets chosen (naively changing period-end to always be the payday would otherwise have broken every ordinary employee's full-month pay whenever payday isn't the last day of the month).

**Same day, real bug found via user report, fixed on both website and App: `normalize_value()` was never ported to either Supabase-direct bridge.** User hit "invalid input syntax for type date" on every website create. Root cause confirmed by direct reproduction via the REST API: an optional date field left blank in a form submits as an empty string `''` (normal HTML form behavior) — the OLD `api.php`'s `normalize_value()` silently converted `'' → null` for every non-boolean field type before ever touching SQL, but neither `js/supabase_bridge.js` nor the later `lib/supabase_bridge.dart` Dart port ever reimplemented this conversion — both were inserting/updating with the raw form data, so Postgres correctly rejected the empty string for `date`/numeric/uuid columns. **This would have hit every single resource with any optional field left blank, not just dates** — reproduced and confirmed the exact fix directly against the REST API (`due_date: ""` → error; `due_date: null` → succeeds) before touching any code, then ported `normalize_value()`'s full switch statement (boolean/tags/json/url/default cases, not just the null-coalescing) to both `normalizeValue()`/`normalizeData()` in `js/supabase_bridge.js` and the equivalent in `lib/supabase_bridge.dart`, wired into both languages' `create`/`update` action handlers before the actual Supabase call, with json/url parse-failure now returned as a sentinel (`undefined` in JS, a shared `invalidFieldValue` const in Dart, since Dart has no bare `undefined`) that both handlers check and turn into a proper `字段 X 格式不对` error instead of ever reaching the database malformed. Rebuilt + reinstalled the Flutter APK with this fix bundled in before the user could hit the identical bug there too (this bug was latent in the App the whole time, just not yet triggered since the App hadn't been used for a create yet). **Lesson for any future "port PHP business logic to a client SDK" work on this project: `normalize_value()`'s empty-string-to-null conversion is easy to forget because MySQL never surfaced it as a bug (MySQL silently coerces empty string for many column types) — Postgres does not, so this class of gap only becomes visible after a Postgres-direct migration, not before. Grep for `normalize_value` in the old `api.php` before assuming any future PHP-logic port is complete.**

**Same day, second follow-up: real latency problem discovered, not just a tunnel blip.** After the tunnel fix, user still got `TimeoutException after 0:00:10.000000` on login. Timed the actual `login` and `dashboard` actions THROUGH the tunnel (not localhost, unlike the earlier "connection confirmed" health-check which was an unauthenticated `me` call that never touches the DB — a real gap in that verification): `login` took ~3s, but `dashboard` (`build_dashboard()`) took **16.4 seconds**. Root cause: every PHP request opens a brand-new PDO/SSL connection to the Supabase pooler in Sydney from scratch (no connection pooling possible — each Apache request is a fresh process), on top of the Cloudflare Tunnel hop, and `build_dashboard()` issues many small sequential queries (one per bank account in `compute_bank_balances()`, plus separate auto-generation checks, category breakdown, EPF cumulative, etc.) — each round trip to Sydney adds up. This is a genuine architectural cost of the MySQL→Supabase migration (local MySQL was sub-millisecond; this isn't) — a client-side timeout tweak alone doesn't fix the underlying slowness, only stops premature failures.

**Immediate fix applied**: bumped `api_service.dart`'s HTTP timeout from 10s to 45s on both `_authCall()` and `call()`. Rebuilt + reinstalled. Dashboard will still visibly take mid-teens of seconds to load — this is now expected/tolerated, not silently masked.

**Real follow-up work if the user wants a genuinely responsive app** (not yet done, don't start unprompted since it's an invasive change to a working function): reduce `build_dashboard()`'s per-request round-trip count, e.g. batch the per-account balance computation into one aggregate SQL query instead of one query per account.

**Process lesson**: after any backend migration that changes latency characteristics (local→remote DB), test the actual client-facing action end-to-end through the real network path (tunnel included, with a real logged-in session hitting real DB queries), not just a fast unauthenticated health check. Also: force-stopping/relaunching the user's app to debug it can interrupt their own in-progress use (happened this session, user was mid-login) — prefer lower-impact diagnostics (logcat by existing PID, passive screenshot) and ask before force-stop when the user might be actively on the phone, per [[feedback_dont_drive_personal_phone_ui]].
