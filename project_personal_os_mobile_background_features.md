**User asked for (verbatim intent)**: steps must track "随时" (any time — app closed, phone locked); reminders must pop as a real notification, stay in the notification shade until the user taps a "✓ done" action (not auto-dismiss), and — first requested as *also* a lock-screen full-screen alarm-style popup with a 5-min auto-dismiss falling back to the persistent notification, then **explicitly walked back** ("算了，你还是做一个notification在上面的通知栏就好了把" — never mind, just make it a plain notification) once the full-screen version turned out fragile to test/debug. **Lesson: when a feature build starts generating repeated debugging rounds, expect the user to eventually ask to cut scope back to the simpler version — don't resist that, it's the right call.**

**Final architecture (2026-09-30, after abandoning `zonedSchedule` — see finding #8 below)**:
- Steps: `flutter_foreground_task` running a real Android foreground service (`foregroundServiceType="health"`), independent background isolate re-initializes its own `Supabase.initialize()` (reads the same persisted-session SharedPreferences, no re-login needed) to upsert `daily_metrics.steps` directly. Android requires a visible ongoing notification for this ("正在记录步数中") — no way to fully hide it; user explicitly accepted this tradeoff. The baseline-reset-at-midnight logic (see [[project_personal_life_os]]) also lives in this same isolate's `onRepeatEvent` (every 30s), using the last-seen raw sensor reading so it resets even if the user hasn't taken a step yet that day.
- Reminders/subscriptions/birthdays: **NOT scheduled via `flutter_local_notifications`' `zonedSchedule()`/`AlarmManager` at all anymore** — that mechanism is confirmed broken on this specific device (see finding #8). Instead, the SAME already-reliable step-tracking foreground-service heartbeat (every 30s) polls Supabase directly for anything due (`reminders` where `is_sent=false AND remind_at<=now`; `subscriptions`/`contacts` within their `remind_days_before` window) and calls `.show()` (confirmed reliable — see #8) directly from the background isolate. Dedup for subscriptions/birthdays uses a SharedPreferences key storing the last-notified target date, so it fires once per occurrence, not every 30s, but still fires even if the exact trigger day was missed (unlike the old exact-equality-day check). `notification_service.dart` now only handles: plugin init, and the "✓ 已提醒" action-button response (`mark_done`) — no longer owns any scheduling.
- The "✓ 已提醒" notification action button itself needed `showsUserInterface: true` (not `false`) to actually respond to taps on this device — `false` (silent background broadcast, no app launch) never fired the handler at all, a second independent unreliability found in the same plugin. `true` opens the app briefly (same `PendingIntent.getActivity()` mechanism already proven reliable for tapping the notification body) — accepted as the tradeoff for it actually working. Cold-start (app fully killed) tap handling needs `NotificationService.handleColdStartLaunch()` called in `main()`, checking `getNotificationAppLaunchDetails()`.

**Real bugs found+fixed this session (not hypothetical, each confirmed via live DB/device checks)**:
1. `bank_accounts.current_balance` (computed from transactions, not a stored column) was never attached in Flutter's generic `ApiService.list()` — mirrors a website JS bug fixed earlier same session; the two client ports had independently drifted. Fixed both.
2. Editing an existing `fixed_deposits.principal` never adjusted the linked opening transaction — confirmed via reading the **original pre-Supabase PHP** `api.php` that this was never implemented, ever, not a migration regression. Now creates a same-day delta transaction (expense if principal increased, income if decreased) instead of silently rewriting the historical opening transaction.
3. `reminders.remind_at` construction (`"$datePart $time:00"`, no UTC offset) let Postgres interpret the naive string as UTC — every reminder fired 8 hours later than the user's intended Malaysia-local time. Fixed by explicitly appending `+08:00` in both bridges' `applyReminderTimeRule()`.
4. Flutter's time-picker for `type: 'time'` fields saved `"HH:MM:00"` (with seconds); the reminders-specific `"only fill in HH:MM"` auto-date-stamping rule matches a strict `^\d{2}:\d{2}$` regex and silently no-ops on anything with seconds, so the raw secondsful string got sent straight to a `timestamptz` column and errored. Fixed the picker to emit `"HH:MM"` (matching the website's native `<input type="time">` output format exactly) — also fixed the same field's edit-mode value-parsing, which crashed (`int.parse` on a date fragment) when the stored value was a full timestamp rather than a bare time.
5. The reminders **list screen showed the raw UTC ISO string** (e.g. `2026-09-29T09:18:00+00:00`) with no local-time conversion — this was the single biggest source of user confusion in the whole debugging session (repeatedly looked like "the time got changed/is wrong" when the underlying data was correct the whole time, just displayed in the wrong unit). Fixed generically for any `time`/`datetime`-typed field in `resource_list_screen.dart`'s `_subtitle()`: full timestamps get `DateTime.parse(...).toLocal()` + `DateFormat('yyyy-MM-dd HH:mm')`; bare time-only values just get seconds trimmed. **Also fixed the on-screen scheduling-diagnostic dialog itself**, which had been showing the scheduled time in raw UTC right next to `DateTime.now()` in local time — two different units juxtaposed, which read as "way off" even when correct.
6. `resource_form_screen.dart` had roughly half its Chinese text corrupted into CP1252 mojibake (see the reversal technique in [[feedback_windows_flutter_toolchain_gotchas]]) — this was the root cause of an earlier, separately-reported "手机很多字显示不出来/乱码" complaint, not a font/emoji-rendering issue as first guessed. Fixed; added a `'color'` swatch-picker field type to the same file while it was open (parity with the website's palette+custom-color picker, was previously a bare text field).
7. R8/ProGuard stripped Gson `TypeToken` info needed by `flutter_local_notifications` in release builds → `zonedSchedule()` crashed with `Missing type parameter.` on every call, in release only (see [[feedback_windows_flutter_toolchain_gotchas]] for the proguard-rules.pro fix). **This fix alone was not enough — see #8.**
8. **Root cause of the whole reminder-notification saga, found 2026-09-30 after the proguard fix above**: even with the crash fixed, `zonedSchedule()`'s scheduled alarm reliably fired on time (repeatedly confirmed via `adb shell dumpsys alarm`'s per-package wake history, e.g. `last -Xm alarm ago` lining up exactly with the target time) but the resulting notification **never posted** — no crash, no log (this device's logcat is filtered, see [[feedback_windows_flutter_toolchain_gotchas]]), the notification channel for it never even got created (checked via `adb shell dumpsys notification --noredact`). Isolated by testing a bare, feature-stripped `zonedSchedule()` call (same failure) vs. a plain immediate `.show()` call (posted correctly, confirmed via the same dumpsys command) — proving the OS/device wasn't blanket-blocking the app's notifications, specifically the schedule+alarm+background-receiver-rebuild code path in this plugin version was silently broken on this device. Fix was architectural (see "Final architecture" above): stop using `zonedSchedule` entirely, poll instead via the already-reliable foreground-service heartbeat and call `.show()` directly.
9. Flutter's generic `'fk'` dropdown field (`resource_form_screen.dart`) **never applied `fk_filter`** (e.g. `{module: 'contact'}` on a tags fk field) — always showed every row of the referenced resource regardless of the config's filter. This is a fundamental gap present since early in the app's life (the `fk_filter` key was never even parsed into `models.dart`'s `FieldConfig`), invisible until this session added several different tag `module` values (`reminder`/`journal`/`contact`, alongside the pre-existing `finance`/`task`/`link`) — first surfaced as "为什么我在联系人那里会看到工作打卡[一个提醒模块的标签]的". Fixed by adding `fkFilter` to `FieldConfig.fromJson` and filtering the cached rows client-side before building dropdown items.
10. Flutter's `AppState.fkCache` is **never invalidated** after create/update/delete — unlike the website's `app.js` which calls `invalidateFkCache(resourceName)` after every mutation. A tag created via "标签管理" wouldn't appear in any other already-loaded form's tag dropdown ("手机版本的都没办法选择标签呢") until a full app restart wiped the in-memory cache. Fixed by adding `AppState.invalidateFk(resource)` (removes just that resource's cache entry) and calling it after every `ApiService.create`/`update`/`delete` in `resource_form_screen.dart`/`resource_list_screen.dart`.
11. The **website** had the mirror-image half of bug #9: the generic FORM field's fk dropdown already correctly used a filtered cache (`loadFkFiltered`), but the **filter BAR's** `fk_select` control (`buildFilterBarHtml` in `app.js`) used the raw unfiltered `fkCache` — same visible symptom (a 联系人 filter dropdown showing a reminder-module tag), different code path. Fixed by having the filter bar look up `fkFilteredCache` under the same `${resource}::${JSON.stringify(filter)}` key the form path already populates.
12. **Reminders' `related_type`/`related_id` fields (a fixed enum + raw-UUID-text-input pair) were removed entirely** per explicit user request ("去掉关联ID，然后关联类型...改成选标签") and replaced with a `tag_id` FK to `tags`, mirroring the pattern transactions/tasks/bookmarks already used. New `tags.module` values added: `'reminder'`. The same tag-ification was then extended to `journal_entries.tags` and `contacts.tags` (previously free-text comma-separated JSONB, `type: 'tags'` field) → single `tag_id` FK each, with new module values `'journal'`/`'contact'`. Safe to do as a hard cutover (drop old column, add new one) because both tables had zero real data at the time. **Any future resource that gets its own tag-module needs a matching `tags.module` CHECK-constraint update in both the live DB and the master schema SQL file, or `tags` creation for that module will fail.**
13. Supabase's PostgREST API layer can serve a **stale schema cache** for a short while after a raw `ALTER TABLE`/`DROP COLUMN` run through a direct PDO connection (not Supabase's own SQL-editor UI) — symptom looked like "the reminders list page hangs forever loading" right after such a migration. Fixed/worked around by running `NOTIFY pgrst, 'reload schema';` once via the same PDO connection immediately after any DDL change made this way. Also see [[reference_supabase_connection_from_this_vm]].
14. Google Play Protect's "App scan recommended" dialog (unrelated to any of the above) intermittently intercepts a freshly-`adb install -r`'d debug/local-signed APK's very first launch, fully blocking the app from opening until the user taps "Scan app" (never "Don't install app" — that one uninstalls it) — a real, recurring friction point when iterating quickly on this device via `adb install` + `adb shell am start`, not a code bug. Screenshotting after each install (with the user's blanket ad-hoc authorization for this debugging session — see [[feedback_dont_drive_personal_phone_ui]]) was the way to catch it, since it silently no-ops `am start` otherwise (app never reaches Dart code, so nothing scheduled/logged).
15. **Effective debugging technique established this session for a device with filtered logcat**: `adb shell dumpsys notification --noredact` (lists every currently-posted notification + its channel, actions, flags — proved whether `.show()`/`zonedSchedule` actually posted anything) and `adb shell dumpsys alarm` (shows pending `RTC_WAKEUP` alarms by `origWhen`/`setAtTime`, plus a per-package "last wake Xm/Xs ago" history) — both work regardless of the logcat filtering and were what actually pinned down finding #8. Combined with directly inserting test rows via PDO + `adb shell am force-stop` / `am start` to trigger a fresh bootstrap, this let most of the reminder debugging happen without needing the user to manually operate their phone at all (only needed them for genuinely UI-only steps like a Vivo settings toggle or confirming a tap worked).

**Payroll (schema-level) additions, same session**: EIS added as a third optional statutory deduction alongside EPF/SOCSO (`salary_profiles.enable_eis`/`employee_eis_percent`/`employer_eis_percent`; equivalent snapshot columns on `salary_payments`). Also added dedicated `socso_contributions`/`eis_contributions` tables (mirroring `epf_contributions`'s pattern but without EPF's 3-way Akaun Persaraan/Sejahtera/Fleksibel split, since SOCSO/EIS don't have sub-accounts) — SOCSO had never had its own contribution-record resource before this, despite EPF having had one for a while; user asked for parity ("需要有个单独的一行，我可以点进去看详细"). Dashboard cards added for both on website + app.

**Resolved by end of 2026-09-30 session**: reminder notifications confirmed actually posting and persisting (via `dumpsys notification`) after the polling-based rewrite (#8); the mark-done action button confirmed working after switching to `showsUserInterface: true`. The ~1-minute picked-vs-stored-time discrepancy from the earlier session was never separately re-investigated and is very likely explained by the raw-UTC-display confusion in finding #5 (i.e. probably wasn't a real bug) — not worth revisiting unless it recurs with a clean local-time comparison.

**Still open**: whether the Vivo-specific OEM battery/autostart settings (电池→后台高耗电/自启动/锁定最近任务) are still necessary for long-running reliability now that the polling approach doesn't depend on `AlarmManager` exact alarms for reminders (steps still uses a genuine foreground service, which still benefits from battery-optimization exemption) — not re-tested after the architecture change, since the polling fix made the point moot for reminders specifically.

**2026-10-01 additions**:
16. User reported (after a day of real use) that steps "stopped updating" overnight/on a different wifi network, suspecting the architecture requires being on the same network as this PC — **false, this is a non-issue to correct confidently**: the app talks directly to Supabase's public cloud endpoint, not this machine, so it works on any network with internet. Checked `daily_metrics` directly and found the background sync actually *had* kept working correctly the whole time (a fresh row synced minutes before the user checked) — the real, confirmed bug was elsewhere (#17). Added a defensive improvement regardless, since it's a plausible contributing risk: `step_service.dart`'s `_syncToServer()` now retries once via `Supabase.instance.client.auth.refreshSession()` before giving up on an upsert failure, in case the background isolate's own `GoTrueClient` auto-refresh timer doesn't reliably fire over long idle/backgrounded periods (unconfirmed whether this was ever the actual cause here, but cheap insurance). Also surfaced (not yet confirmed by the user) a separate, device-specific possibility worth checking if sync issues recur: Vivo phones have a **background-data restriction separate from the battery-optimization setting already covered** (通常在 流量管理/应用联网管理 里，不是电池设置) that can block network access for backgrounded apps while still allowing local-only work (sensor reads, notification text updates) — matches the exact "notification updated, DB didn't" symptom pattern precisely, so worth checking first if this recurs.
17. **The actual confirmed bug** behind "步数都没更新" this time: the dashboard's step display (`dashboard_screen.dart`) wraps `StepService.todayStepsStream` in a `StreamBuilder` with `initialData: StepService.todaySteps`, and `StepService._todaySteps` was a non-nullable `int` defaulting to `0`. Every fresh app-process start shows this hardcoded `0` until the background isolate's *next* periodic push arrives (up to 30s later) — and critically, `builder: (_, snap) => snap.data ?? metric?['steps']` treats the stream's `0` as a present, non-null value, so it **never falls back to the reliable DB-fetched `metric['steps']`** even though that value was sitting right there and correct. Net effect: looked exactly like "sync stopped," especially right after reopening the app, when the DB was actually fine the whole time. Fixed by making `StepService._todaySteps`/`todaySteps` nullable (`int?`, starts `null`) so the `??` fallback to the DB value actually engages until a real push arrives. **General lesson for this codebase: any "cached live value ?? freshly-fetched value" fallback pattern is silently broken if the cached value's "nothing yet" state is represented by a real value (like `0`) instead of `null`/absence** — worth checking other screens with a similar live-stream-over-DB-value overlay pattern for the same mistake.
